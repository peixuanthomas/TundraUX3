# 程序自更新

更新工作流位于 `app::update`；CLI 运行更新助手，Shell 保存设置并安排退出和重启。

## 下载、构建和替换

Linux 的“设置 → 更新 → 更新模式”保存到 `config.toml` 的 `linux_update_mode`，默认 `release`。

- 正式版：读取 GitHub 最新已发布正式 Release，按版本号和提交判断是否需要更新。下载 Linux x86_64
  便携包及对应校验文件，校验 SHA-256，提取 Shell、CLI 和完整 Vim 运行目录，检查提交号、更新协议及 Vim 资源后替换。不需要 Rust 或 Python。
- 测试版（`beta`）：固定检查 `master` 最新提交，界面显示提交哈希作为小版本标识；下载该提交的源码，
  使用本机已有 Rust 工具链编译，再显式运行 `scripts/build-vim.py` 构建源码所固定的 Vim 后替换。
  Vim 构建需要 Python 3.12 和 C 构建工具：Linux 使用 make、ncurses 开发文件，Windows 使用 MSVC C++ Build Tools。
  保留 API 失败时的 Git 查询后备方式，不安装编译器或调用 sudo；普通 Cargo 构建不会下载 Vim。
- 切换模式会清除旧检查结果并重新检查；同版本号但提交不同的测试构建可以明确选择替换为正式版。
  下载或编译过程中不可切换。所有下载与编译都写入用户缓存目录。

Windows 继续使用已有的默认分支源码编译更新，不显示 Linux 模式开关。

更新助手保存旧程序及旧 `vim/`，等新 Shell 报告启动成功后才清理备份。替换失败、启动失败或启动超时会同时恢复程序和 Vim；旧版没有 Vim 目录时，回退移除本次新增目录。更新中断后，下次启动会按安装目录内的记录继续或恢复，包括 Vim 目录已经发布但记录尚未更新的情况。

Vim 目录必须包含可执行文件、完整运行资源、许可和 `UPSTREAM.json`；缺少 Vim 的旧便携包不能用于本版本更新。下载包内的上游信息允许后续正式版本升级 Vim pin，精确版本和功能由新源码的构建脚本与新 Vim 宿主核对。更新不要求源码目录或安装目录下存在 assets；默认主题、自定义主题和用户数据均不参与复制、替换或回滚。启动时仍按原有方式加载本地资源。

新更新使用协议 v3，Vim 事务状态为必需字段；旧版 v2 更新程序会在校验新程序时拒绝该协议，避免只替换两个程序而遗漏 Vim。因此，从 v2 版本升级时需要完整解压一次新便携包。已有 v2 事务只允许回退、恢复或清理，不会开始安装其旧准备目录，也不会删除或替换原有 Vim 目录。助手取自已校验的新 CLI；更早协议的记录会明确拒绝，保留原文件。Linux 使用无 `.exe` 后缀的程序名并保留执行权限；助手通过 exec 接替原进程，在新 Shell 退出前持续等待，使更新后的程序继续使用前台终端。

Windows 更新时，原 Shell 先停止界面和后台任务，再等待更新助手；助手等待更新后的 Shell（或回滚恢复的 Shell）退出，两者都不读取终端输入，避免 PowerShell 提前恢复并与程序争用终端。原 Shell 仍在运行的备份可以被读取，但不能直接作为 `ReplaceFileW` 的替换源，因此回滚使用备份的副本。仍被运行中进程占用的备份保留到以后启动时清理；更新中断后的恢复也沿用同样的等待方式。

macOS 暂不提供程序自更新。更新测试见[测试说明](update-tests.md)。

## 取消与清理

检查、下载、Git 后备查询、构建、解压、校验和复制都检查取消信号。等待 HTTP 或子进程时也能中断；Windows 和 Linux 只结束这次任务启动的进程树，随后回收进程。界面区分取消中、已取消和失败。

取消后清理本次任务创建的工作目录和未应用的准备目录；已有安装程序及用户文件不参与清理。已准备的替换事务先写入 `Cancelled` 记录，再删除目录。若标记写入失败，保留目录和错误供重试；目录删除失败也显示原因及残留位置。启动时 `Cancelled` 记录只触发清理，不触发替换。

准备成功与取消同时发生时，Shell 接受结果前再次核对取消状态，取消不能设置自动重启标记。替换助手已经接手后，继续沿用现有安装、启动确认和回滚流程。更新仍只运行一项。
