### 外层 watchdog 与托管协议

- `[x]` 进程结构按 `tundra launcher/watchdog → bundled wezterm-gui → tundra-shell` 组织。
- `[x]` Shell 使用 session ID 和原子 JSON outcome 文件返回逻辑结果。
- `[x]` `0` 表示正常关闭，`74` 表示显式重启，`75` 表示已确认 reset。
- `[x]` 结果缺失、格式错误、session 不匹配、启动失败、非预期退出码和信号都归类为异常。
- `[x]` 自动恢复窗口为 60 秒，三次退避为 0.5、2、5 秒；显式 restart/reset 不占异常预算。
- `[x]` Enter 人工恢复后进入 60 秒 probation；期间再次异常直接返回 panic 页，稳定超过 60 秒才清除预算。
- `[x]` launcher 持有运行标记、记录 stale launcher 和私有诊断日志。
- `[x]` Shell 托管模式关闭重复的 unclean-run tracking，并停止自我 exec/spawn 重启。
- `[x]` Shell 仍保留 managed task、panic boundary、operation journal 和 terminal recovery。
- `[x]` watchdog incident 新增精确 session ID，recovery 投影只接受当前 session 的事故。
- `[x]` 托管 host protocol 已升至 v2，并由 Shell、launcher、构建产物 marker 和打包脚本共同拒绝 v1 或不匹配实现。

### 目标体验

- Windows 双击 `tundra.exe`、macOS 双击 `TundraUX3.app`、Linux 点击应用图标后，立即出现定制 WezTerm 并进入 Tundra Shell。
- 用户不需要预先打开终端，不需要输入 `./tundra`，启动过程中不出现系统默认终端、普通 shell prompt 或 Windows 控制台闪窗。
- 发行物采用“单一可见入口”：WezTerm、`tundra-shell`、`tundra-cli`、assets 和动态库作为包内私有运行时，不要求物理单文件。
- 第二次双击只激活已运行窗口，不创建第二套会话。

### 启动与 Watchdog 架构

- 新增 GUI launcher `tundra`，作为持续驻留的 WezTerm 外壳宿主：
  - Windows 使用 GUI subsystem；macOS 使用 `.app`；Linux desktop entry 使用 `Terminal=false`。
  - 从自身安装目录解析私有运行时，预检 WezTerm、Shell、CLI、assets 和协议版本。
  - 只使用绝对路径启动定制 WezTerm，并将固定的 `tundra-shell` 作为其唯一前台程序；禁止 PATH、用户 WezTerm 配置和系统终端回退。
- 进程树固定为 `tundra/watchdog → bundled wezterm-gui → tundra-shell`。Shell 的 stdin/stdout 必须连接 WezTerm PTY 后才启动。
- 外层 `tundra` 成为生命周期级 watchdog，负责运行标记、进程树收割、异常重启、事故报告和恢复页。Shell 内部仅保留 managed task、panic boundary、operation journal 与终端恢复，并在托管模式关闭重复的 unclean-run tracking。
- 平台层增加受控子进程句柄：Windows 使用 Job Object；Unix 使用独立进程组及父进程存活约束。注销、关机或外层退出时先等待 Shell 清理终端，2 秒后仍未退出则终止整棵进程树。
- 托管协议使用 session ID 和原子结果文件区分 Shell 退出与 WezTerm 自身崩溃：
  - `0`：正常关闭。
  - `74`：显式重启。
  - `75`：已确认的存储重置。
  - 其他退出码、信号、启动失败或结果文件缺失：异常。
- 异常在 60 秒内最多自动重启 3 次，退避为 0.5、2、5 秒；显式重启和 reset 不占预算。

### WezTerm Kernel-Panic 恢复页

- 重启预算耗尽后，外层停止启动 Shell，改以 WezTerm 私有 recovery 模式打开全屏诊断页。该模式不创建 PTY 子进程，也不依赖已经崩溃的 Shell。
- 页面采用 Linux kernel panic 风格，但明确标识为应用会话故障：
  - 黑色全屏背景、粗红色警戒边框和红色顶部状态带。
  - 主标题：`TUNDRAUX3 SESSION PANIC`。
  - 次标题：`SYSTEM HALTED — AUTOMATIC RECOVERY LIMIT REACHED`。
  - 白色等宽正文、黄色关键状态；不用闪烁或仅依赖颜色表达。
  - 显示 UTC 时间、incident ID、故障来源、退出码/信号、组件版本、重启次数、脱敏摘要和少量 traceback 预览。
  - 底部持续显示 `PRESS ENTER TO RESTART TUNDRAUX3`。
- Enter 是页面唯一恢复操作：
  - 首次按下后立即锁定输入并显示 `RESTARTING...`，防止按键重复。
  - WezTerm recovery 模式以特殊状态返回外层，由外层冷启动完整 WezTerm/Shell 进程树。
  - 人工重启不立即重置自动恢复预算；若 60 秒内再次失败，直接回到 panic 页。稳定运行超过 60 秒后才恢复正常预算。
  - Escape 和普通窗口关闭不静默忽略故障；系统注销、关机仍必须正常响应。
- 若 WezTerm recovery 模式本身无法启动，才回退到平台原生 critical dialog，并给出 incident ID。

### Panic 二维码

- Panic 页右侧由 WezTerm 原生像素渲染器绘制二维码，不使用终端字符拼接，确保在不同字体、DPI 和最小终端尺寸下仍可扫描。
- 二维码内容是离线纯文本，不是 URL，不发起网络请求。载荷格式固定为 `TUNDRA-PANIC-CAPSULE/1`，包含：
  - incident/session ID、UTC 时间；
  - Tundra、Shell、WezTerm 版本或固定提交；
  - 故障来源、退出码/信号、恢复次数；
  - 脱敏 panic 摘要；
  - 最多 8 个经过规范化的 traceback frame；
  - `Full details: Diagnostics > Logs > <incident-id>`。
- 载荷最大 1,200 UTF-8 bytes，超限时优先裁剪 traceback 并写入明确的 truncated 标记。使用高纠错等级、整数像素缩放、四模块 quiet zone 和纯黑白模块。
- 二维码及页面禁止包含用户名、绝对本地路径、环境变量、argv、token、剪贴板、原始输入或完整 stderr。完整报告继续保存在 Diagnostics 的 logs 中，并沿用管理员详情权限。
- watchdog 新增只读、版本化的 `RecoveryHandoffV1` 投影，只从已经脱敏的 incident 生成页面和二维码数据；WezTerm 不直接解析完整事故 JSON。
- 报告缺失或损坏时仍显示通用 panic 页，并生成仅含退出状态和“详细报告不可用”的最小二维码。

### 构建与发行

- 构建流程生成完整可运行目录，而不是把裸 `tundra-shell` 当最终产品：
  - Windows 根目录只暴露 `tundra.exe`，私有 runtime 包含 WezTerm、Shell、CLI、assets 和 DLL。
  - macOS 输出标准签名 `.app` bundle。
  - Linux portable/deb 将 launcher 放在公开入口，私有组件放入 Tundra 专属 runtime/libexec 目录。
- Shell 与 CLI 保持同目录关系，确保内嵌 Command Line 能找到 `tundra-cli`；launcher 显式设置私有 assets 路径。
- `third_party/wezterm` 先在 fork 中实现托管启动、退出传递、recovery 页面和二维码，再更新主仓库固定 gitlink。CI 拒绝未初始化、脏状态或提交不匹配的子模块。
- 先产出三平台 WezTerm experimental artifacts；稳定发布仍保留现入口，直到完成 Windows/macOS/Linux 的 IME、键鼠、全屏、多显示器、注销和关机实测。

### 测试与验收

- 从 Explorer、Finder、GNOME/KDE 直接双击或点击应用，确认只出现定制 WezTerm，并直接进入 Tundra Shell；全程无默认终端、控制台闪窗或中间 prompt。
- 在未安装 WezTerm、PATH 被污染、用户存在冲突 `.wezterm.lua` 的环境中仍使用包内终端。
- 覆盖正常退出、74/75、Shell panic/abort、WezTerm 崩溃、启动失败、3 次重启预算、Enter 人工恢复、系统关机和父进程崩溃，确认没有孤儿进程。
- 为 panic 页面增加状态机测试、各尺寸/DPI 截图测试、缺失/损坏报告降级测试及敏感字段泄漏测试。
- 对每个二维码进行自动回读，断言解码文本与 `RecoveryHandoffV1` 完全一致；再进行不同手机、缩放比例、明暗环境下的人工扫描。
- 检查重启后的 `Diagnostics > Logs` 能按 incident ID 找到完整报告，而 panic 首屏和二维码只包含受限摘要。

## 继续构建验证时的推荐执行顺序

1. 确认主仓库位于包含提交 `8ae28cd` 和后续 native recovery 改动的分支；不要丢弃已恢复的顶层 `third_party/wezterm` 源码。
2. 初始化并验证嵌套子模块与顶层 pin：

   ```powershell
    git -C third_party/wezterm submodule update --init --recursive
    git submodule status -- third_party/wezterm
    bash scripts/verify-wezterm-submodule.sh
   ```

3. 预期 status 以空格开头并显示：

   ```text
    e378176fd3aa8204ace298157599b5a3b8496ca4 third_party/wezterm
   ```

4. 验证已提交的 managed patch，然后构建：

   ```powershell
    $managedPatch = (Resolve-Path patches/wezterm-managed-v1.patch).Path
    git -C third_party/wezterm apply --check $managedPatch
    git -C third_party/wezterm status --short
    bash scripts/build-bundled-wezterm.sh
   ```

   `status --short` 必须为空。应直接使用 build helper，由它负责再次检查、临时应用和反转补丁，并在反转失败或残留 dirty 状态时让构建失败。

5. 在 MSVC + Strawberry Perl 和完整嵌套依赖下重新运行 fork 的 fmt、test、check 与 native recovery 验证；当前已知基线为 native recovery 17/17、kiosk config 2/2、最终 GUI SHA-256 `561569e605eab91ad6e4d0c590da6cec2fafb178378ec8f9a423371cf5638bd9`。
6. 重新运行完整 Rust 测试、严格 clippy、三平台目标编译和 fork 测试。
7. 使用三平台 assembler 生成 experimental artifacts。
8. 完成真实桌面、生命周期、二维码、IME、多显示器、签名和安装/升级验收。
9. 只有全部门禁通过后，才讨论替换稳定发布入口。

## 恢复工作时的安全约束

- 不提交 `third_party/wezterm` 的删除。
- 不把不同 commit 冒充固定 pin。
- 不将系统 WezTerm 或 PATH fallback 引入产品启动链。
- 不让 recovery 页面直接读取完整 incident JSON。
- 不在页面或二维码中加入路径、环境、argv、token、clipboard、原始输入或完整 stderr。
- 不在完成人工 GUI/生命周期验证前修改 stable package/release workflow。
- Windows/macOS 签名、macOS notarization、第三方许可和运行时依赖闭包未完成前，产物只能标记 experimental。
